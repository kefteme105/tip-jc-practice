## Полученный результат

Клиент загружает задачи и категории, фильтрует на сервере, создаёт и редактирует задачи, меняет статус, удаляет записи с подтверждением и восстанавливает учебный набор. После изменения выполняется новый GET. Снимок не дополняется локально и id назначает сервер.

Изменения переживают перезагрузку клиента, пока работает тот же процесс API. После перезапуска сервера возвращается исходный набор. ПР8 продолжает интерфейс ПР7 и работу с API из ПР5–6.

## Архитектура

Компоненты отвечают за отображение, управляемые поля и пользовательские действия. `useTaskData` хранит последний успешный snapshot, status, error, mutationError и pending. `task-api` содержит операции предметной области; `api-client` отвечает за HTTP, тайм-ауты и разбор ответов. Конфигурация создаёт стабильную ссылку api вне React.

Эффект зависит от api, q, completed, priority, categoryId и revision. Изменение любого поля фильтра или refresh запускает новое чтение. Cleanup отменяет старый GET и делает его результат неактуальным. Snapshot не входит в зависимости: иначе успешное чтение запускало бы само себя.

## Загрузка и изменения

Каждое чтение имеет собственные active и AbortController. Как успех, так и catch проверяют актуальность, поэтому поздний ответ не меняет новое состояние. Старый успешный снимок сохраняется при loading и при ошибке GET.

Мутация имеет отдельный контроллер в ref, который устанавливается до первого await. Два синхронных вызова создают одну операцию; второй возвращает false. Смена фильтров отменяет только чтение. Размонтирование отменяет и чтение, и запись.

Успешный POST/PATCH/DELETE возвращает true и повышает revision. Последующий GET использует текущие фильтры. Если этот GET не удался, запись всё равно считается успешной; ошибка чтения показывается отдельно. Автоматического повторного POST нет. При ошибке самой записи возвращается false, форма сохраняет черновик, pending снимается.

## Контрольные вопросы

1. Эффект синхронизирует компонент с API после рендера. Запрос в теле компонента повторялся бы при каждой перерисовке.
2. Cleanup вызывается перед новым запуском эффекта и при размонтировании.
3. Callback эффекта должен вернуть cleanup или ничего. Async-функция возвращает Promise, поэтому асинхронная работа вынесена внутрь.
4. Нужны api, поля фильтров и revision. Snapshot является результатом, а не условием чтения.
5. Новая ссылка api в каждом рендере вызывала бы повторные загрузки.
6. Отмена не гарантирует, что уже завершившийся или подставной запрос не вернёт результат; active дополнительно защищает состояние.
7. Поздняя ошибка тоже могла бы испортить актуальный успешный результат.
8. Дополнительный setup/cleanup в StrictMode обнаруживает отсутствующую очистку; мутации не выполняются при монтировании.
9. State обновляется не сразу. Ref блокирует повторный вызов синхронно до await.
10. True означает подтверждённую запись. Неудачный последующий GET означает только ошибку обновления списка.
11. Сервер мог сохранить запись до потери ответа; повтор POST способен создать дубликат.
12. Фильтр меняет выборку, а не намерение пользователя сохранить задачу.
13. Отмена ожидания не откатывает уже выполненное сервером действие.
14. meta.total — количество записей текущей выборки, а не всего хранилища.
15. jsdom не проверяет настоящий внешний вид, видимый фокус, DevTools, браузерный CORS и реальную навигацию/preview.
